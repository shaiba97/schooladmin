
## 2026-09-27 - Backend endpoints for the academics rework (verified)

### Structure
- **Model names unchanged.** Kept `SchoolClass`/`Section`/`SectionSubject`/`TimetableEntry`
  rather than the spec's `Class`/`ClassSubject`/`ClassTimetableEntry`. Sections stay as
  rows for enrolment/assignment integrity; they are only removed from nav and the
  class-detail tab strip.
- **Timetable is class-keyed, not section-keyed.** `TimetableEntry.classId` is NOT NULL and
  `sectionSubjectId` became nullable, so a slot can be written directly from the grid.
  `UNIQUE (tenantId, classId, dayOfWeek, periodNo)` makes a whole-cell batch an upsert set.
- **Sport lives in `SportTimetableEntry`,** not `TimetableEntry`: it has `slotNo` (max 2/day)
  instead of periods, and its rules (same sport never fills both slots) would otherwise
  pollute lesson validation.

### Behaviour decisions
- **`POST /subjects/batch` auto-provisions a section named "A"** for any class that has none,
  and reports the class ids back under `sectionsCreated`. Without this, multi-assign silently
  did nothing for section-less classes (2 of 2 existed at the time). It is never silent: the
  response says exactly which classes were touched.
- **Batch payloads are the complete grid.** Missing cells are deleted, present cells upserted.
  This is what makes "Save Timetable" one request; a stale row cannot survive a save.
- **Lesson cells must name a subject AND a teacher,** and the teacher must be assigned to that
  subject for that class (`SectionSubject`), otherwise 400. Break cells must carry neither.
- **Teacher double-booking is a UI warning, not a server 409.** It spans classes, which a
  class-scoped save cannot see; the teacher tab derives and flags it.
- **Delete guards are explicit.** Deleting a subject that is still assigned to classes returns
  409 with a count (the FK would otherwise cascade silently); used by a timetable returns 409.

### Bug found and fixed during verification
`withTenantRead` runs on the default connection, so reading *inside* a `withTenant`
transaction returns pre-commit state. `PUT /timetable/batch` and `POST /sport-timetable/batch`
were returning `[]` even though they had written correctly. Fixed by extracting
`readClass`/`readSport` and calling them on the transaction handle.
